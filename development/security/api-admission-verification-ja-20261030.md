# 複数アカウントによる処理集中への対策（2026-10-30）
## 本番へ反映した内容
Data APIの各要求の前にstudy_api_admissionを実行する。通常枠は全アカウント合計6処理、各アカウント2処理。同じアカウントの複数タブ・複数セッションも同じ枠を共有する。未ログインは全員で2枠を共有する。サーバー用の要求も通常の全体枠を共有する。
DBに登録されたオーナーかつ有効なauth.sessionsのセッションを持つ場合だけ、復旧用の専用1枠も使える。ユーザーが変更できるmetadataの役割には依存しない。
待機列を積み上げず、空きがなければHTTP429の日本語メッセージを返す。PostgreSQLのトランザクションロックを使い、完了・例外・切断で自動解放する。利用者データ・IPアドレス・永続カウンターは増やさない。既存の匿名3秒・認証済み8秒の処理時間上限は維持する。
アカウントを50個に増やしても全体6枠は増えない。これは同時処理数の上限であり毎分の回数制限ではない。正常利用の混雑でも429になることがある。ゲーム描画・乗客・音声などの機能は削除していない。

## 本番検査
- anon権限で通常の関数呼び出し成功、アカウント枠と全体枠のロック2個を確認。
- 1つの管理用検査トランザクションで匿名2枠と全体6枠を短時間確保。実際の公開RESTエンドポイントstudy_security_statusはHTTP429（個別上限）となり、解放後HTTP200。
- 別の検査では全体6枠だけを確保。同じ公開RESTエンドポイントがHTTP429（全体上限）、解放後HTTP200。
- 終了後の該当ロック0。検査用アカウントの作成、利用者データの書換え、50件の実負荷投入はしていない。
- 初回のSQLコネクタ同士の並列検査は同時実行を確保できずHolder not readyとなった。これを成功扱いにせず、独立したHTTPクライアントとSQLトランザクションによる上記検査に切り替えた。
- authenticatorのpgrst.db_pre_request設定を読み戻して確認。
- セキュリティアドバイザー確認済み。新しい公開SECURITY DEFINERに対するanon/authenticated実行可能の注意が各1件増える。これは匿名要求も受け付ける入場判定に必要な権限。関数はデータを返さず、固定search_pathで、所有者確認以外に利用者の表を書き換えない。既存のRLS/有料パスワード漏洩検査の注意は変更していない。

## 範囲と限界
この前処理はPostgRESTのData API向け。Authのログイン・登録、Storageの画像転送、Realtime、GitHub Pagesの静的配信、Edge Function全体の実行時間を共通に遮断する仕組みではない。EdgeからData APIに入るDB処理には適用されるが、認証検証などDB処理の前のコストまでは止めない。既存の入力上限・画像容量上限・管理者追加認証・データ復元・不正操作検知を維持する。
無料構成でネットワーク回線やプラットフォーム全体へのDDoS耐性を保証するものではない。少数枠を連続占有する攻撃による一時的な利用不能も完全には防げない。通常のアクセス集中を不正アクセスと断定して自動メンテナンスにする変更はしていない。
有料サービス・プラン変更・外部AIは使用していない。
