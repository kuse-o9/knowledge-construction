# 3D接続・トンネル負荷の修正（2026-10-31）
依頼受領21:48JST、全ゲーム確認の追加指定21:54JST。無料の既存構成で実施。

## 症状を区別
- 単体WebGL2成功：ブラウザーがその時点で小さな接続を作れたことだけを示す。重い3D全体の初期化・メモリー余裕・継続描画の成功保証ではない。
- Web page caused context loss and was blocked：Chromiumが接続喪失後にそのサイトのWebGL作成を拒否した場合に出す文字列。単にトンネルの中だからと断定しない。
- GL_VENDOR/GL_RENDERER=Disabled：その接続をブラウザーが無効と報告。アプリのコードだけで有効化したり組織の制限を回避したりしない。

## 修正
Cesium1.117のトンネル・線路沿いの地形切り抜きは、120mの表示窓更新ごとにClippingPolygonCollectionを作り直していた。同版の署名付き距離テクスチャーは最大4096x4096のRED/FLOAT（64MiB相当）。新方式は同じコレクションを所有し続け、removeAll/addで更新する。解像度・切り抜き範囲・線路・車両・乗客・ホーム・床・壁・屋根・照明を減らしていない。
同版は頂点数が同じだと更新しないため、直前のGPU用頂点数と同じ場合だけ既存ポリゴンを1件重複追加して再計算を促す。重複は同一領域であり切り抜く和集合は変わらない。私有フィールドの書換えや解像度の低下はしない。
トンネルの12m／160m区画は、以前と同じ中心位置・距離条件を空間索引で探す。全線の各区画を窓ごとに再走査する処理を削減し、採用順を維持。
明確なブラウザーブロック・無効化・組織ポリシーのエラーでは、初期化の3パターンを繰り返さず最初の失敗で停止。同じページ内でも再作成を連打しない。診断ボタンの結果も再利用。通常の一時失敗での再試行・保存・地図モードは維持。
こもれび島は接続喪失時に入力と描画更新を停止し、現在のアカウントのローカル保存と従来のクラウド保存を試みる。保存成功を確認できない場合は成功と表示しない。ブラウザーからの復旧通知後も本人の再開ボタン操作を待つ。
会社別車両基地も明確なブロック時に再初期化を重ねず、全23階の選択・路線への移動は維持。

## 検査
- 36表示窓で修正前の切り抜き和集合・床／壁／屋根／照明が一致。コレクション作成37→1、座標系計算279020→76164。実GPUのVRAM測定ではなく所有回数・CPU計算の検査。
- 14路線・27方向・10365地点で線路沿い切り抜き、有限な座標、破棄時の整理を確認。peakEntities1425、reused10696。
- ブロック／Disabled／組織ポリシーの3例は1回で停止し、同ページでの再作成が増えない。通常失敗の3回上限、地形通信再試行、保存後の後片付け・再試行も確認。
- 車両基地の7動作検査と3階キャッシュ上限に合格。GPU無効のままページだけで回復したことにする古い期待は、再起動前に無理な再作成をしない検査に改めた。正常な新規起動も確認。
- こもれび島の接続喪失・同じ喪失の重複・保存・入力停止・復旧後の明示再開を模擬検査。モジュール構文検査も実施。
- 山手線、中央快速・各停と延長分岐、京浜東北、総武快速、ゆりかもめ、あずさ、かいじの実際の入口と共通処理の結び付きを確認。車両基地・こもれび島も対象。
- 手元のchuo-west.binが切れていたため、現在のGitHubのblob SHAと一致する元データから検査用コピーだけを復旧。本番の模型バイナリーは変更していない。

物理GPUでの初期化・全区間の実時間走行・長時間VRAM測定はこの環境では未確認。利用者が報告した機器で今回の白画面を再現して消えたとは保証しない。ブラウザーがすでに接続をブロック／無効化している場合は、Chrome chrome://settings/system、Edge edge://settings/system の設定確認とブラウザー再起動が必要な場合がある。
